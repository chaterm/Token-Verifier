# 探针机理与检测出发点

> 本文讲**为什么这样测**。工具怎么用见 [README](../README.md)，
> 字段定义见 [SPEC-CONFIG.md](./SPEC-CONFIG.md) 与 [SPEC-RAWDATA.md](./SPEC-RAWDATA.md)。

## 一、出发点：黑盒之下能观测到什么

买到一个 API 端点，你能看到的只有：请求进去，响应出来。看不到权重、看不到量化方案、
看不到采样参数、看不到中间是否插了一层改写。

而端点方有很强的动机做替换：把大模型的请求路由到小模型、上更激进的量化、
削减思考预算、截断上下文。这些改动都能显著降低成本，而且**在单次对话里几乎看不出来** ——
因为大模型的输出本来就是随机的，你没法凭一次回答判断它是不是变了。

所以问题不是「这个回答好不好」，而是：**在只能看到输入输出的前提下，
有没有什么量是稳定的、可测的、且换了模型就一定会变的？**

有。答案是**采样分布**。

### 核心洞察

给定一组固定的权重、一个固定的采样参数，模型在某个 prompt 上的下一个 token
分布是确定的。你采样一次得到一个随机结果，但采样很多次，得到的**经验分布**
会稳定收敛到那个确定的分布。

这个分布对模型的一切都敏感：

| 端点做了什么 | 分布会怎样 |
| :--- | :--- |
| 换成另一个模型 | 完全不同的分布 |
| 换成同家族的小模型 | 分布形状明显改变 |
| 上更激进的量化 | 权重被扰动，分布随之偏移 |
| 悄悄改了 temperature / top_p | 分布的集中度改变 |
| 在前面插了一层改写 prompt | 输入变了，分布也变了 |

于是黑盒检测有了立足点：**不去判断回答的好坏，只去比较分布的形状。**

这也是本工具与 benchmark 的根本区别。benchmark 回答「这个模型有多强」，
需要标准答案、需要评分标准，而且对小幅降级极不敏感 —— 一个被量化砍过一刀的
模型在多数 benchmark 上可能只掉一两个点，落在噪声里。分布比较回答的是
「这还是同一个模型吗」，它不需要标准答案，而且对权重扰动异常敏感。

### 为什么必须对标，不能给绝对判据

分布本身没有「正确值」。JSD = 0.08 是大还是小？取决于这个模型自身的随机性
有多大。有的模型天生分布很集中，重复采样几乎一致；有的模型分布很散。
所以任何绝对阈值都是无意义的。

必须**拿同一套题、同一套参数，在一个可信端点上也测一遍**，两个分布对比。
这就是 rawData 存在的理由：它是一份可复现、可分发的「对标基线」。

**这也解释了为什么工具设计成无状态的两步。** 采集与比较分离，
使得基线可以离线分发 —— 官方发布某模型的 rawData，用户下载来跟自己买的
端点比。用户也可以自己建基线：今天测一次存下来，一个月后再测一次跟它比，
就能发现端点在这期间是否悄悄变了。

## 二、什么模型都能测

**这个工具对模型没有任何要求。** 它不需要知道模型的架构、参数量、训练数据、
能力水平，也不需要模型「答对」任何题。

它唯一的要求是：**同一套刺激，在待测端点和对标端点上各跑一遍。**

这一点比它听起来更重要，尤其在 agent 场景。

### 以工具调用探针为例

假设你给模型一组它**从未见过、完全虚构**的工具，问它一个需要用工具的问题。
模型可能选错工具、可能编造参数、可能干脆不调用。

**这完全不影响检测。** 因为对标端点在同样的题目上也会犯同样类型的错误 ——
如果它们真是同一个模型，那么「选哪个工具」「参数怎么编」这两件事的分布
应该一致。检测比的是**行为的分布**，不是**行为的正确性**。

反过来说，正因为不要求答对，题目可以设计得非常刁钻：越是模型没有强先验的
题目，回答的随机性越大，分布的信息量越高，指纹越锋利。**一道所有模型都能
稳定答对的题，是一道没有鉴别力的题。**

这个思路对所有探针都成立：

- 极短答案探针不在乎模型选了哪个数字，只在乎它选各个数字的比例
- 长上下文探针不在乎召回率是 90% 还是 30%，只在乎两侧的召回率是否一致
- 思考强度探针不在乎模型思考得对不对，只在乎它花了多少思考 token

所以无论是通用对话模型、推理模型、代码模型、agent 专用模型，
还是你自己微调的模型，都可以测。**唯一的前提是能拿到一个可信的对标基线。**

## 三、探针清单

每个探针独立可选，可任意组合。启用哪些、每个用什么题库、跑几次、
在哪些上下文长度下跑，全部由使用者决定。

| 探针 | 作用 | 观测量 | 统计方法 |
| :--- | :--- | :--- | :--- |
| `onetoken` | 主指纹。识别模型替换、量化改变、采样参数被改 | 极短答案的取值 | 分布间 JSD |
| `tokenizer` | 识别分词器改变、prompt 被中间层改写 | 服务端上报的输入 token 数 | 逐题整数相等 → 卡方 |
| `needle` | 识别上下文被截断、长上下文能力降级 | 埋点标记是否被召回 | 命中率 2×2 卡方 |
| `think-effort` | 识别思考被关闭或预算被削减 | 思考量（token 数或思考文本字数，按协议） | 分布比较，按强度与协议分组 |
| `toolcall` | 识别工具调用行为改变，适用 agent 场景 | 选了哪个工具、参数是否合法 | 选择分布 + 合法率 |

下面逐个讲机理。

### onetoken —— 主指纹

**做法**：让模型输出一个取值空间有限的极短答案 —— 一个 0-100 的随机数、
一个字母、一个颜色词、一次抛硬币。温度设 1.0，同一题重复几十次，
统计各取值出现的频次，得到一个经验分布。两侧分布算 JSD，值域 [0,1]。

**为什么用极短答案**：长回答的自由度太高，两次回答几乎不可能字面相同，
无法做频次统计。而「说一个 1 到 100 之间的随机数」这种题，取值空间只有 100 个，
几十次采样就能勾勒出分布形状。**把一个自由生成问题压缩成一个可统计的离散分布，
这是整个方法的关键一步。**

**为什么温度必须是 1.0**：温度 0 的贪心解码每次都输出概率最高的那一个 token，
分布退化成一个点 —— 信息量从「整个分布形状」坍缩成「众数是什么」。
而分布形状恰恰是最敏感的那部分。配置校验会对温度低于 0.5 发警告。

**为什么这类题特别有鉴别力**：模型对「随机说一个数」没有强先验，
输出高度依赖权重的细微结构。实践中不同模型在这类题上的偏好差异极大 ——
有的偏爱 42、有的偏爱 7、有的分布相对均匀。这些偏好是权重的直接指纹。

**能抓到什么**：换模型、换量化、被改采样参数。这是最主要的探针。

**抓不到什么**：如果端点方知道题目内容并针对性地缓存答案分布，理论上可以伪装。
但这需要为每道题预先构造分布，成本远高于诚实提供服务。

### tokenizer —— 输入侧指纹

**做法**：构造对分词敏感的输入 —— 中日韩文字、emoji、全角字符、
代码片段、JSON 结构，只看服务端在 usage 里上报的**输入 token 数**，
逐题比对两侧的整数是否相等。

**为什么这个探针值得单列**：它不看输出，只看输入侧的一个整数。
噪声极低 —— 同一个分词器对同一段文本的切分是确定的，
所以两侧应该**完全相等**，不相等就是真不一致。因此它只需重复 1 次，
成本极低，而结论极硬。

**不需要本地分词器**：工具不做本地分词，也不需要知道端点用的是什么分词器。
它只比较两个端点上报的数字是否一致。这让探针对任何模型都适用，
且没有任何依赖。

**判等按取值集合，不按条数**：`repeats > 1` 时一个 cell 有多条观测，
两侧比较的是去重后的取值集合是否一致 —— 条数差异来自 repeats 配置
（`--allow-subset` 下两侧可以不同）或个别请求失败，不是分词器差异。
正常情况下同一 cell 内服务端上报值恒定，集合退化为单值。

**能抓到什么**：换了模型家族（分词器不同）、改了分词器配置、
以及一个很隐蔽的情况 —— **中间层悄悄改写了你的 prompt**（加系统提示、
做安全过滤、压缩上下文）。prompt 被改了，token 数就变了。

### needle —— 上下文完整性

**做法**：在一段长上下文中埋入标记，要求模型把它读出来。
比较两侧的召回率。

**标记的确定性派生**：标记由 (题目 ID, 埋点位置序号) 经哈希算出，不以明文出现在题库文件里，
也不出现在公开的 rawData 里。这样公开基线数据不会让被测端点预知标记内容。

**一题多埋点**：题目用 `needle_positions` 声明若干相对位置（如 `[0.25, 0.5, 0.75]`），
每个位置埋一个独立派生的标记。一个埋点就是一个统计单元 —— 观测按位置逐点记录
命中与否（`{"matched": [true, false, ...]}`），报告能看出「从哪个深度开始丢」。

**关键是分档位测**：同一道题在多个上下文长度下各测一遍。
一个声称支持 256K 但实际在 128K 以上就开始截断的端点，
只有分档测才能定位到拐点。上下文档位是所有探针共享的一个轴，
不只 needle 能用。

**统计**：一个埋点单元在其 cell 的全部 repeats 都被召回才算「命中」，
两侧各统计命中/未命中的埋点单元数进 2×2 卡方（小样本自动 Fisher）。
两侧都不假定全中 —— 基准侧自己漏掉的埋点不会制造假警报，比的是召回率的差异。

**池化的独立性假设**：卡方把各埋点单元当作独立观测直接池化，但同一 cell 的
repeats 内各埋点并不独立 —— 一个只复述开头内容的端点会让所有浅埋点命中、
深埋点全漏，单元间存在正/负相关，池化计数会偏离真实方差。对当前
α=0.01 + 「宁可漏报不误报」的取向，这是可接受的保守简化。将来样本充足时
可以换成逐单元检验 + Fisher 合并（think-effort 用的正是这个结构，原语现成）。

**能抓到什么**：上下文被静默截断、长上下文注意力质量降级、
声称的窗口大小造假。

**注意**：这个探针的基本观测是二值结果，噪声偏大，需要较多重复与较多埋点才稳定。

### think-effort —— 思考行为

**做法**：在题目上标注思考强度级别，观测响应里的思考 token 数分布。

**为什么需要它**：思考型模型的推理过程是主要成本来源，
因此也是最有动机被削减的地方。一个端点可以接受你的 `high` 强度参数、
返回格式完全正确的响应，但实际只用了 `low` 的预算。
输出内容看起来正常，只有思考 token 数会露出来。

**强度是符号级别，不是具体数值**：题目只写 `low` / `medium` / `high`，
由各协议的配置映射成自己的具体值。这让同一道题可以跨协议、跨厂商使用 ——
题库完全不需要知道某家厂商的思考字段叫什么。

**统计**：cell 按 (题目, 档位, 强度级别, 协议) 分组，逐 cell 对两侧的思考量做
Mann-Whitney U 检验（非参数，对思考量这类偏态分布稳健），
再用 Fisher 法合并各 cell 的 p 值为探针级统计量。

**观测单位由协议静态决定**（`unit` 字段，不做运行时回退）：

| 协议 | 单位 | 来源 |
| :--- | :--- | :--- |
| `openai-chat` | `tokens` | `completion_tokens_details.reasoning_tokens` |
| `openai-responses` | `tokens` | `output_tokens_details.reasoning_tokens` |
| `anthropic-messages` | `chars` | 交付的思考文本 rune 数（thinking 块 / thinking_delta） |

Anthropic 的 usage 只有 `input_tokens` / `output_tokens`，思考 token 计入输出、
无独立字段 —— 但 thinking 块完整交付，文本长度是思考量的可用代理。
Mann-Whitney U 是秩检验，只要求 cell 内两侧单位一致：cell_key 按协议分层后
天然满足，tokens 与 chars 永远不会进同一个 cell（这与 tokenizer 按协议分层
是同构的做法；代价是样本按协议切碎，`repeats` 需按最稀的协议份额配够 `min_n`）。

两个单位的口径也不同：`tokens` 是「服务端声称思考了多少」（计费口径），
缺失/为零记观测错误 —— 区分「没上报」与「零思考」；`chars` 是「客户端实收
多少思考文本」（交付口径），**0 是有效观测** —— 基准侧交付了思考文本而
B 侧没有时，分布检验直接判出，记观测错误反而会把降级藏成 inconclusive。
交付口径还能多抓一种降级：网关声称 reasoning_tokens 很高但把思考流截断了。

注意 `openai-responses` 的 ReasoningContent 是 reasoning **summary** 而非
原始思考，字数在该协议下不代表思考量 —— 所以它的单位仍是 `tokens`
（usage 里有），字数通道只给真正交付原始思考文本的协议用。

**能抓到什么**：思考被静默关闭、思考预算被削减、思考强度参数被忽略、
声称的思考量与实际交付的思考文本不符。

### toolcall —— agent 场景

**做法**：给定一组工具定义和一个需要用工具的问题，观测：
选了哪个工具（分布）、参数是否**语法合法**（工具名在生效工具集内且参数是
合法 JSON object；不做 schema 字段级校验）、是否发起并行调用
（`num_calls`，进报告明细）。

**为什么它在 agent 场景特别重要**：agent 的行为几乎完全由工具调用决策构成。
一个在对话上表现正常的替换模型，可能在工具选择上有明显不同的偏好 ——
而这恰恰是 agent 可靠性的核心。

**工具可以完全虚构**：如前所述，模型不认识这些工具没有关系。
它选错工具、编造参数，对标端点也会以相似的方式选错、编造。
比的是分布的一致性。这反而让题目设计更自由 ——
可以专门设计一些模型没有强先验的工具集，来放大分布差异。

**统计**：两个证据分量逐 cell 计算 —— 工具选择分布的 JSD（距离语义）与
参数合法率的池化 2×2 卡方（alpha 语义）；两个分量共用一个阈值，
任一分量超阈即 fail。观测取首个工具调用（多调用时 `parallel=true`、
`num_calls>1`），模型完全不发起工具调用记观测错误，由可用率指标另行反映。
JSON 报告里 `statistic` 只承载 JSD 均值分量，`ratio` 取两分量的更差者 ——
合法率分量主导时二者会「对不上」（`statistic` 很小而 `ratio` > 1），
`note` 里印了两个分量各自的值，消费方聚合时应以 `ratio` 为准。

**能抓到什么**：agent 行为漂移、工具调用能力降级、
以及一个很实际的情况：端点声称支持工具调用但实现质量不同。

## 四、阈值：不提供默认值，必须由使用者标定

**工具不带任何默认阈值。** 缺少任一待比较探针（或其任一档位）的阈值，
`compare` / `run` 会拒绝执行并退出（`exit 2`），指名缺哪个。设置方式：
配置文件的 `thresholds` 段，或命令行 `--threshold <probe>=<value>`，命令行优先。
键支持档位级覆盖：`<probe>.<bucket>`（如 `onetoken.8000: 0.12`）只对该
`context_bucket` 生效，档位须在该探针的 `context_buckets` 内，未覆盖的档位
回退探针级值。报告的每一行（多档位时含档位子行）都会印出实际用的值与它的
来源（`config` / `flag`），所以永远不存在「不知道这个判定是按什么标准做的」。

**统计量在档位内聚合，跨档位取最差。** 下文各探针的「探针级统计量」
（JSD 均值、池化卡方、Fisher 合并 p 值）均只在单个 `context_bucket` 内计算；
声明多档位的探针逐档位独立判定，探针级结论取最差档位（详见 SPEC-CONFIG §7
与 DATAFLOW §3.4）。对 p 值类探针，这意味着单档位检验的样本量比池化时小、
功效更低，但「短上下文正常、长上下文回归」不再被跨档位稀释。

理由：一个阈值意味着「多大的差异算异常」，它取决于三件事 —— 模型自身的随机性
有多大、你的部署环境有多稳定、以及你的容忍度。一个天生分布很散的模型，用 0.15
会误报；一个非常稳定的模型，用 0.15 会漏报。给一个看起来合理的默认值，等于替
使用者做了一个他不知道自己在做的判断。

标定方法很直接：**对同一个已知可信的端点采集两次，用得到的统计量作为「正常波动」
的量级**，再在它之上留出余量。这也是为什么工具鼓励用户自建基线 —— 那份数据
同时能用来标定阈值。

下表是从参考实现的生产使用中观察到的经验值，**不是默认值**，仅作首次标定的起点：

| 探针 | 统计量 | 经验起点 | 说明 |
| :--- | :--- | :--- | :--- |
| `onetoken` | JSD 距离 | 0.10 – 0.15 | 用于告警时取更严的一端 |
| `tokenizer` | 卡方显著性水平 α | 0.01 | 整数比较，噪声极低 |
| `needle` | 卡方显著性水平 α | 0.01 | 单 cell 二值，噪声偏大 |
| `think-effort` | Mann-Whitney U + Fisher 合并 α | 0.01 – 0.05 | 逐 cell 检验后合并 |
| `toolcall` | JSD 距离 + 合法率 α | 0.05 – 0.15 | 一值两用；以合法率为主线时取 0.01 – 0.05（见 SPEC-CONFIG §7） |

**阈值不参与可比性判定**。它不写进采集计划、不参与 digest，
所以改阈值不会让你手里的 rawData 与官方基线变得不可比。
可比性只由采集参数决定，判据是独立的一层。

## 五、题库：外部文件，完全自己定制

题库不编进二进制。它是一份外部 YAML 文件，由配置里的 `suite.path` 指向，
覆盖上述五个探针的题目。规范见 [SPEC-SUITE.md](./SPEC-SUITE.md)。

把它放在外部是刻意的：题库是检测内容本身，编进二进制会让「改题目」变成
「发版本」，也会让不同版本工具产出的 rawData 之间多一层隐式差异。外部文件让
题库可审查、可 diff、可随官方基线一起分发。

题目文本、取值空间、归一化规则、埋点方式、工具定义、思考强度标注，全部可自定义。
典型场景：

- **贴合自己的业务场景**。如果你的 agent 用的是一组特定的工具，
  用那组真实工具做题目，得到的指纹比通用题库更贴近你实际关心的行为。
- **提高鉴别力**。发现某类题目在你的模型上分布特别散（即特别敏感），
  就多写这类题。
- **规避针对性缓存**。公开题库理论上可以被端点方针对性优化。
  自己的私有题库不存在这个问题。
- **测试特定假设**。怀疑端点在某类输入上做了改写，就针对性设计题目。

> **官方发布的参考 rawData 配套发布采集时所用的题库文件。**
> 这是为了让所有官方基线之间可比、也让任何用户都能用同一份题库去对标。
> 用自定义题库采集的数据，只能与同样使用该题库采集的数据比较 ——
> 题库标识参与采集计划的 digest，两侧不一致会被直接拒绝并指出冲突。

## 六、这套方法的边界

诚实地讲清它测不到什么，比夸大能力更有用。

**不能证明底层模型的真实身份。** 它只能说「这两个端点的行为分布有显著差异」
或者「没有显著差异」。前者是有力的差异证据，后者不等于身份证明 ——
一个足够精心构造的伪装仍然可能通过。

**没有可信基线就什么也做不了。** 所有结论都是相对的。
如果你手里没有一份可信的 rawData，这个工具帮不了你。

**分布比较需要足够的样本量。** 用几个样本估出来的分布形状不足以支撑判定，
样本量不足的 cell 会被明确标为 insufficient 并剔除，而不是勉强给个结论。

**传输指标不是身份证据。** 可用性、延迟、TTFT、吞吐这些量会被完整采集
和分层统计，但它们主要反映网络路径与瞬时负载。把它们算进判定，
会让一个真实的同模型端点仅因为机房不同就被判为不一致。
所以它们默认只作描述性对比输出，除非你显式为它们设定阈值。

**结论有时效性。** 一次判定是特定时间窗口、特定配置下的测量结果。
端点可以在你测完之后再改。这正是为什么这个工具被设计成能嵌进监控循环
反复执行，而不是做一次性认证。

## 七、当前未实现、计划中的能力

以下能力在设计中已留出位置，但当前阶段不做：

| 计划中的能力 | 说明 |
| :--- | :--- |
| **聚合纯净度分** | 把各探针判定合成一个 0-100 的分数。需要标定数据来支撑各探针权重与掉分曲线。当前每个判定已经携带 `ratio`（观测值与阈值的比率，`ratio > 1` 恒等价于失败），聚合层将来可以直接消费它，无需重跑采集 |
| **从实测方差自动推导阈值** | 用多次采集的方差自动给出建议阈值，替代手工标定 |
| **时序稳定性轴** | 参考实现中权重最高的一条判据：当前这次是否跑出了自身历史的自洽范围。需要多次采集的历史序列，当前单次 rawData 不含 |
| **更多协议适配** | 当前设计覆盖三种主流协议形态，新增协议是加一个适配器，不改探针 |
| **更多探针** | 探针是插件式的。结构化输出一致性、多轮对话行为、缓存命中行为等都可以作为新探针加入 |
| **官方参考 rawData 库** | 为常见模型发布基线，配套发布采集所用的题库文件 |
